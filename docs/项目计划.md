当前运行约束：

- 不自动下载、更新或删除用户引擎源码，不自动安装训练环境；绑定已有解释器并显式诊断。
- 提交时固定安装实例、源码 revision、Python 环境记录、adapter 版本和配置 hash；修改默认实例不影响已提交任务。
- 关闭桌面窗口不结束 API、supervisor 或训练；`connection_lost` 不自动重跑，人工核实原进程和子进程已退出后才能解除队列阻塞。
- 不保证中断保存 checkpoint，不提供 checkpoint 自动续训或完整训练状态恢复。
- 运行中禁止直接切换 `data_root`；迁移需停止相关后台服务并通过启动参数指定新目录。
- 当前 Kohya 适配不接受含子目录图片的数据集；输出目录不可放入源码、数据集、基础模型或应用数据目录。
- GPU 监控使用可选低频 `nvidia-smi`，不可用显示未知，不在应用进程加载训练模型。
- 前端方案已经确定，不追加选型原型或额外性能验证；常规功能测试和构建不改变前端样式。

## 1. 项目定位

LP LoRA Trainer 是一个从零开始构建、独立运行的本地 LoRA 训练管理应用。它以成熟训练引擎为计算后端，提供统一的可视化界面、任务管理、数据集管理，以及引擎安装、维护、更新和回滚能力。

**本项目不依赖 ComfyUI，不是 ComfyUI 插件，也不需要安装或启动 ComfyUI。**

“给 ComfyUI 训练 LoRA”指训练产物以在 ComfyUI 中使用为主要目标，而不是把训练流程放进 ComfyUI。训练器与 ComfyUI 之间只有可选的文件交付关系。

第一批引擎规划为：

- Kohya：界面使用该名称，默认直接适配其底层 `sd-scripts` 训练入口，不运行原有 GUI。
- AI Toolkit：本文将用户所说的 `aitool` 暂按 `ostris/ai-toolkit` 理解，适配其原生配置和命令行入口。

### 1.1 核心目标

1. 让用户通过统一界面完成数据准备、配置、训练、监控和结果管理。
2. 将训练计算交给成熟引擎，不重新实现训练算法。
3. 隔离应用与各训练引擎的依赖，避免更新互相破坏。
4. 将引擎版本管理作为核心能力，支持同一引擎多版本共存、明确选择、任务固定版本、兼容矩阵与回滚。
5. 尽可能减少包装层对训练速度、显存、CPU、内存与磁盘的额外消耗。
6. 保留足够的配置、环境和产物记录，使训练能够追溯和尽可能复现。

### 1.2 首版不做

- 不做 ComfyUI 插件、节点、扩展 API 或内部模型管理集成。
- 不重写训练循环、优化器或 LoRA 算法。
- 不运行 Kohya、AI Toolkit 的原有完整 Web UI。
- 不默认支持多人协作、云平台、分布式训练或远程集群。
- 不承诺任意引擎版本、任意模型架构都可无适配使用。
- 不把所有引擎参数强行归一，也不保证不同引擎的配置完全等价。
- 不为了预览采样图额外启动推理服务或加载另一份模型。

## 2. 产品形态

### 2.1 确定形态：独立桌面应用

前端方案确定为 **pywebview 桌面窗口 + Vue 3 / TypeScript / Vite 前端 + 独立 Python 后端**。直接按此方案实施，不安排前端技术选型原型或独立性能验证阶段，也不将这些验证作为开始开发的前置条件。

用户通过应用自己的桌面窗口使用训练工作台，默认不打开外部浏览器。桌面层只承担窗口生命周期、原生文件选择及必要的系统交互，不承担训练计算或引擎适配业务。

Vue 前端构建为静态资源，由 Python 本地服务提供；pywebview 加载本机页面。服务默认只监听 `127.0.0.1`，不向局域网暴露。启动入口统一拉起所需进程并打开窗口，用户无需分别启动前后端。

Windows 使用 `edgechromium` / WebView2 渲染路径；启动时检查必要运行时，缺失时提供明确的安装提示，不悄悄降级到旧 IE 渲染器。首版不引入 Electron，也不并行维护另一套桌面 GUI。

前端构建工具仅用于开发和打包，使用已构建应用不需要常驻 Node.js 服务。业务与窗口层保持解耦，保留以后复用为浏览器模式的空间，但浏览器模式不是首版默认入口。

### 2.2 窗口与训练生命周期

- 默认一个应用主窗口、一个 WebView，页面切换不创建新的 WebView。
- 关闭窗口不等于停止训练，停止训练必须通过明确的任务控制操作执行。
- 有活动任务时，关闭窗口后独立监管进程和训练进程继续运行；再次启动应用重新连接。
- 桌面层和应用后端退出不能级联结束正在运行的监管进程；空闲进程可正常退出。
- 最小化窗口时降低界面更新频率，暂停非必要图表、图片预览和目录刷新；不影响任务日志落盘。

### 2.3 与 ComfyUI 的关系

- 训练模型与 LoRA 输出使用用户指定的文件路径。
- 用户可选择一个 ComfyUI LoRA 目录作为发布目标，也可完全不配置。
- 完成训练后默认只登记产物，不自动复制所有 checkpoint。
- 用户显式选择某个产物后，应用才执行发布操作。
- 发布前检查目标文件名，默认禁止覆盖同名文件；先写入临时文件，再完成最终落盘。
- 同时提供模型架构、基础模型标识、训练摘要及使用说明。
- 只对经过验证的架构组合标注 ComfyUI 使用兼容性；文件扩展名正确不代表任意基础模型都能加载。
- 不调用 ComfyUI 的私有接口，不修改其源码，不向其 Python 环境安装任何包。

若用户同时运行 ComfyUI 或其他 GPU 程序，本项目只能检测资源和提示风险，不能保证阻止外部程序占用 GPU。

## 3. 总体架构

```text
桌面窗口：pywebview + Vue 3 工作台
├─ 数据集
├─ 训练配置
├─ 任务监控
├─ 结果管理
└─ 引擎管理
         │ 本地 HTTP + SSE 事件
         ▼
独立应用后端
├─ API 与输入校验
├─ 配置与能力查询
├─ 数据集与产物索引
├─ 引擎安装与环境诊断
└─ 任务查询与控制
         │ 本地 IPC
         ▼
轻量任务监管进程
├─ 队列与任务状态
├─ 训练进程生命周期
├─ 日志、指标与心跳
└─ 持久化与重连
         │ 原生配置文件 + 参数列表
         ├─ Kohya 适配器 → 独立环境 → sd-scripts
         └─ AI Toolkit 适配器 → 独立环境 → 原生 CLI
```

### 3.1 模块边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| 桌面层 | 窗口、原生选择对话框、受限系统交互 | 训练计算、引擎业务、任意 Python 调用 |
| 前端 | 交互、配置编辑、日志与结果展示 | 执行训练、直接访问任意文件 |
| 应用后端 | API、校验、安装管理、索引与查询 | 加载训练模型、执行训练 step |
| 任务监管 | 排队、启停、身份核实、日志与状态 | 修改训练算法 |
| 引擎适配器 | 能力声明、配置转换、命令生成、指标解析 | 独立维护一份训练引擎分支 |
| 原生训练进程 | 模型加载、训练、采样与保存 | 依赖本项目的窗口或界面连接 |

应用与监管代码不得为管理功能导入 `torch`、加载模型或初始化 CUDA。

### 3.2 进程与持久化原则

- 关闭桌面窗口不影响训练；再次启动窗口后重新连接任务。
- 应用后端重启后，可重新连接仍在运行的监管进程。
- 监管进程按需启动；首版默认一个 GPU 上只运行一个训练任务。
- 训练任务使用独立输出目录，日志不依赖桌面窗口或前端连接。
- 监管进程不能因应用后端退出被意外终止；Windows 与 Linux 分别验证生命周期行为。
- 监管进程负责活动任务状态写入，后端通过 IPC 请求任务变更，避免双方竞争更新同一任务。
- IPC 仅允许本机访问，并使用随机令牌鉴权；不暴露为公共控制接口。
- 不承诺监管进程或整机崩溃后训练仍能运行，此时只能核实状态或从有效保存点恢复。

## 4. 可视化工作台

### 4.1 数据集页面

- 添加本地目录，引用原文件，不默认复制数据集。
- 展示图片缩略图、尺寸、数量、caption 和分组信息。
- 检查损坏图片、缺失 caption、异常尺寸与可疑重复项。
- 支持单张 caption 编辑、批量标签替换与修改预览。
- 保存修改前备份或可回退记录，避免无提示覆盖源文件。
- 显式触发扫描；大目录采用分页索引，不在每次刷新时全量遍历。
- 数据集快照优先记录相对路径、大小、修改时间及配置；内容哈希作为可选项。
- 快照不默认复制图片，因此不能保证源文件被外部修改后仍可完全复现；需要时支持冻结副本。

自动打标、裁剪和增强后续作为独立预处理任务加入，不在浏览数据集时隐式加载模型。

### 4.2 训练配置页面

参数分三层：

1. 基础层：底模、架构、数据集、输出名称、步数、学习率、Rank 等。
2. 高级层：优化器、精度、缓存、梯度检查点、保存与采样策略等。
3. 原生层：引擎专属参数、最终原生配置及启动命令预览。

能力由“引擎版本 + 模型架构 + 平台 + 验证档案”决定。不可用参数隐藏或说明原因，不能生成明知不支持的配置。

提供可解释的默认预设，但不把“低显存”“高质量”等预设当作对所有硬件与模型有效的保证。

### 4.3 任务页面

- 任务队列、阶段、状态、启动时间与输出目录。
- 进度、速度、Loss、预计剩余时间及资源监控。
- 原始日志查看、搜索和导出。
- 采样图、checkpoint 和错误摘要。
- 请求停止、强制终止，以及基于有效保存点创建恢复任务。
- 指标无法可靠解析时显示“未知”，不能伪造进度或预计时间。

### 4.4 引擎页面

- 已安装版本、代码来源、Python 与依赖信息。
- 安装、诊断、检查更新、候选版本验证、切换、回滚与清理。
- 导入已有引擎目录和 Python 可执行文件。
- 显示兼容状态：已验证、实验性、未经验证。
- 不把“安装成功”直接当作“训练兼容性验证通过”。

### 4.5 结果页面

- 按任务查看产物与采样图。
- 对比同一任务中不同 checkpoint 的采样结果。
- 查看最终配置、引擎版本、环境摘要及基础模型来源。
- 导出训练记录、定位文件、选择产物发布到 ComfyUI 或其他目标目录。
- 基础模型来源、架构及使用约束必须与产物一起保留。

## 5. 引擎适配设计

### 5.1 统一契约

每个适配器实现以下能力：

```text
探测安装与版本
声明支持能力
校验配置
生成原生配置
构建启动参数
解析日志与指标
识别训练产物
声明停止与恢复语义
执行诊断与最小验证
```

引擎可通过外部进程接口接入。业务层不得直接导入引擎的 Python 模块，以降低依赖耦合。

### 5.2 配置结构

```text
任务公共信息
├─ 名称、数据集引用、模型引用、GPU、输出目录

明确可映射的训练参数
├─ 学习率、步数、Rank、精度等

引擎专属参数
└─ 原生配置结构与高级选项
```

每份配置必须带有 `schema_version`。公共字段只有在语义确实一致时才映射到不同引擎。

切换引擎时：

- 明确展示成功转换的字段。
- 对不支持或不等价的字段提示用户。
- 不静默丢弃参数。
- 不保证任意原生配置可跨引擎转换。

### 5.3 版本化能力与兼容矩阵

维护以下维度：

```text
引擎 revision × 适配器版本 × 模型架构 × 操作系统 × 环境档案
```

兼容状态分为：

- 已验证：有对应测试记录。
- 实验性：可尝试运行，但尚未完成验证。
- 原生配置模式：允许高级用户运行，不声称统一界面完整支持。

优先通过 CLI、配置和输出文件适配上游。只有必要时才加入小范围、可追踪、可撤销的兼容补丁，避免维护庞大的上游分支。

### 5.4 目录边界：一个适配器目录对应一种引擎

- `engine/` 放训练引擎本体；允许将已有引擎目录直接复制进来。
- `adapters/` 放本项目维护的接口适配代码，一个子目录对应一种引擎，而不是一个引擎版本。
- 同一种引擎的多个安装实例共享对应适配器，由适配器内部的版本规则处理差异。
- 适配器目录内可以包含原生配置模板、能力声明、环境档案和日志解析规则，不能混入完整引擎源码。
- `adapters/base.py` 只定义公共契约，不代表一种引擎。
- `engine/` 中的目录名只是安装实例名称，不作为识别引擎类型或版本的唯一依据。
- 新增已支持引擎的版本通常只需复制或安装新的引擎目录；新增一种尚不支持的引擎则需要新增对应适配器。
- 不为了每次上游版本更新复制一整套适配器，也不要求每份引擎源码都修改成某个固定内部布局。

## 6. 引擎版本、环境与更新管理

### 6.1 隔离环境

应用环境与每个训练引擎环境分别管理。默认每个引擎安装实例使用独立环境，优先共享下载缓存而不是可变的运行环境。只有依赖、安装方式与代码路径绑定均验证兼容的环境档案才能共享；不能仅因引擎名称相同或依赖文件相似就复用环境。

```text
<data_root>/
├─ envs/<engine>/<environment_id>/
├─ manifests/
├─ datasets/
├─ jobs/<job_id>/
├─ cache/
└─ state.sqlite
```

引擎源码默认位于项目根目录的 `engine/`（即 `engine_root`），也允许在设置中迁移到其他磁盘。上述 `data_root` 只管理环境、记录、缓存与任务数据，不再设置第二套 `engines/` 源码目录。

安装清单记录代码来源、可核实的 commit 或本地源码指纹、Python、PyTorch、CUDA wheel 类型、依赖快照、适配器版本和验证结果。

CUDA wheel 类型与系统驱动分别检查，不假定用户必须安装完整 CUDA Toolkit，也不自动修改系统显卡驱动。

### 6.2 更新流程

```text
检查版本
→ 下载到候选目录
→ 创建或选择匹配环境
→ 安装与静态校验
→ 入口检查
→ 按需运行小规模训练验证
→ 标记候选版本可用
→ 用户切换默认版本
```

要求：

- 禁止在运行中环境上原地更新。
- 排队和运行任务都固定引擎 revision，不跟随默认版本变化。
- 更新失败不能破坏旧版本。
- 切换默认版本不改变既有任务。
- 回滚切换版本引用，不尝试逆向修改依赖。
- 被任务或保存档案引用的环境不能直接清理。
- 下载支持进度、错误反馈与可重试；离线情况下仍可使用已安装环境。
- 更新检查与训练执行解耦，不因为检查失败阻止本地训练。

### 6.3 复制即发现：简化引擎接入

推荐入口是把完整引擎目录直接复制到 `engine/` 的一个子目录，例如：

```text
engine/
├─ kohya_ss/          # 一份 Kohya 安装
├─ kohya_ss-old/      # 另一份 Kohya 版本
└─ ai-toolkit/        # 一份 AI Toolkit 安装
```

每个一级子目录代表一个安装实例。目录名可由用户决定，无需改成 commit，也无需手动编写注册文件。上游源码目录结构保持原样；识别其内部训练入口由适配器负责。

发现流程：

```text
复制完整引擎目录到 engine/
→ 启动时或点击刷新时发现目录
→ 通过静态文件特征匹配适配器
→ 读取版本信息或建立本地源码记录
→ 检查、选择 Python 解释器与运行环境
→ 标记为可运行，或提示缺少的依赖
→ 用户选择该安装实例启动训练
```

约束：

- 自动发现不等于自动执行。识别阶段只检查目录和文件，不导入或运行未知引擎代码。
- 多个适配器匹配或无法可靠识别时，允许用户手动选择引擎类型；不靠文件夹名字强行猜测。
- 复制了源码且已有环境可用时，验证后即可使用，不强制再次 Git clone 或重新安装。
- 只有源码、没有可用依赖时，登记为“已发现，环境未就绪”，提供选择已有 Python 或创建独立环境的引导。
- 不把随目录复制来的 `.venv` 默认判定为可用；必须验证解释器、路径绑定和必要依赖。
- 没有 `.git` 的压缩包或源码副本仍允许接入；版本显示为用户标签和可核实的源码指纹，不能伪造 commit 或兼容状态。
- 本地指纹范围由适配器声明，覆盖训练入口、相关源码和配置定义，排除模型、输出、缓存与环境；仅在发现、显式刷新及启动校验等必要时更新，不能持续全量扫描。
- 安装清单保存在 `data_root/manifests/`，默认不向引擎源码写入本项目专属文件。
- 复制进来的目录默认采用“用户管理源码”模式：不自动拉取更新、不覆盖源码、不自动删除；运行环境可另行授权由应用管理。
- 用户要维护新版本时，优先复制到新的子目录，避免改动已被任务固定的安装实例；活动训练期间不得由应用更新该目录。

仍支持直接选择 `engine/` 以外的已有目录和 Python 可执行文件，按外部引用方式登记，默认只检测和使用。

托管安装是另一种便捷入口：用户选择版本后由应用下载到 `engine/` 的新实例目录，并完成环境准备。用户复制和应用安装最终使用同一套安装实例模型，而不是两套训练流程。

### 6.4 多版本管理：核心能力

版本管理不是“升级到最新版”，而是允许同一引擎的多个固定版本同时保留，并选择其中一个执行任务。

支持的版本来源：

- 上游发布版本或 Git tag：用于人类可读的版本选择。
- 分支：作为发现新版本的渠道，不作为任务的最终运行标识。
- 指定 commit：用于固定具体代码快照。
- 复制或引用的本地安装：能核实时记录 commit；无 Git 信息时记录本地标签、源码指纹与“上游版本未核实”状态，不伪造版本号。

来自 Git 的安装必须把 tag 或分支解析为具体 commit；同名 tag、分支与“最新版”都可能变化，不能作为不可变身份。本地无 Git 副本使用源码指纹记录实际代码，而非强制要求 Git 仓库。若引擎需要子模块，检查所需内容是否完整，并在可核实时记录对应 revision。允许的兼容补丁必须记录内容指纹。

### 6.5 版本实体与安装实例

将以下概念分开，避免把代码版本与 Python 环境混为一谈：

| 实体 | 主要信息 | 用途 |
| --- | --- | --- |
| 引擎定义 | `engine_id`、类型、代码来源、适配器 | 区分 Kohya、AI Toolkit 及允许的来源 |
| 代码版本 | 来源、请求的 tag/分支、解析后的 commit、子模块与补丁指纹 | 标识实际运行代码 |
| 安装实例 | `installation_id`、代码版本、环境 ID、路径、验证状态 | 标识真正可启动的一套安装 |
| 默认选择 | 每个引擎当前默认的安装实例 | 为新配置提供默认值 |
| 任务绑定 | 安装实例、代码版本、环境与适配器快照 | 保证任务不受后续切换影响 |

同一个 commit 可以有多个安装实例，例如不同 Python 或 PyTorch 环境。它们不能因为代码版本相同就被视为完全等价。

安装状态、验证状态和默认标记分开保存：“已安装”不表示“已验证”，“默认”也不是安装生命周期状态。

### 6.6 版本选择与切换规则

版本选择优先级：

```text
任务显式选择 > 训练预设中固定的安装实例 > 引擎默认安装实例
```

- 创建草稿时可以采用默认版本，但提交任务时必须解析为具体安装实例并保存快照。
- 没有已解析且可用的安装实例时，不允许进入队列。
- 默认版本切换只影响后续配置选择，不改写已排队、运行或完成的任务。
- 已绑定安装实例缺失或失效时，任务明确报错，不自动替换为最新版。
- 从历史记录重新训练，优先使用原安装实例；若改用其他版本，必须作为新的任务记录。
- 切换版本后重新进行能力与配置校验，不假定同一引擎不同版本的参数完全兼容。
- 回滚是选择先前保留的安装实例，不是对当前环境做反向卸包。
- 外部环境在启动前重新核实代码与依赖；发现变化时提示用户并重新确认，不继续冒用旧快照。

### 6.7 存储复用、清理与界面

优先共享 Git 下载缓存、包下载缓存和模型文件引用；托管代码快照与环境安装完成后按不可变方式使用；用户管理的副本在启动前核实是否变化。不能为节省空间而牺牲版本隔离。

引擎页面按“引擎 → 代码版本 → 安装实例”展示，显示：

- 版本名称、短 commit、代码来源和安装时间。
- Python、PyTorch、CUDA wheel 类型及环境位置。
- 已安装、安装失败等生命周期状态。
- 已验证、实验性、未经验证等兼容状态。
- 是否默认、被哪些任务引用、代码与环境磁盘占用。
- 安装、诊断、设为默认、复制为候选安装、回滚和卸载操作。

删除保护：

- 排队、准备或运行任务引用的安装实例禁止删除。
- 默认安装实例须先取消默认或切换默认，才能进入卸载流程。
- 历史任务或保存档案引用的实例不能直接清理；后续如提供解除保留操作，必须确认其会削弱重现能力，并保留版本与环境元数据。
- 卸载一个实例不能删除其他实例仍依赖的环境或缓存。
- 用户复制或外部引用的源码只删除本应用中的登记，不删除用户目录；应用创建的环境可在引用检查与确认后清理，用户提供的外部 Python 环境不删除。
- 训练产物和任务记录不随引擎卸载而删除。

版本目录与已安装状态应在离线时可用；检查上游新版本是可选网络操作，不影响已固定版本的训练。

## 7. 任务生命周期

### 7.1 状态机

```text
草稿 → 校验 → 排队 → 准备 → 运行 → 成功
                           ├→ 失败
                           ├→ 停止中 → 已停止
                           └→ 连接丢失 → 核实实际状态
```

准备阶段包括配置落盘、路径检查、环境核实与 GPU 可用性检查。准备失败不记为成功启动。

### 7.2 每个任务保存的内容

```text
job.json            任务配置、版本引用、数据集记录
config.native.*     最终原生配置
command.json        启动参数与非敏感运行信息
stdout.log          原始日志
metrics.jsonl       可解析指标
artifacts.json      checkpoint、采样图及有效性记录
runtime.json        进程身份、心跳与恢复核实信息
```

SQLite 保存任务状态、索引及引用关系；模型、大图和完整日志保存在文件系统中。

日志需有容量管理，前端只读取增量或尾部；任何清理策略都不能无提示删除模型和训练状态。

### 7.3 停止与恢复

必须区分：

1. 请求正常停止。
2. 强制结束进程。
3. 从 LoRA 权重开始新的训练。
4. 恢复优化器等完整训练状态。

仅在适配器确认支持时展示对应操作。不能把这些操作统一称为“暂停/继续”，也不能承诺停止时必定生成完整 checkpoint。

强制终止必须提示保存中断风险。重连时使用任务 ID、PID、进程创建时间和心跳联合核实，不能仅凭 PID 判断进程身份。

Windows 要管理训练子进程树，避免只结束启动器却留下训练进程。监管进程持有训练进程树的生命周期控制权，不把它绑定到桌面窗口或应用后端退出事件。

## 8. 性能策略与验收

### 8.1 设计策略

| 方面 | 策略 |
| --- | --- |
| 训练计算 | 原生引擎执行，不包装训练 step，不代理张量 |
| 显存 | 后端与监管进程不初始化 CUDA、不加载模型；WebView 渲染可能使用 GPU 资源，不宣称整个界面零显存 |
| 日志 | 持续读取，批量落盘，前端限流，与训练计算解耦 |
| 指标 | 优先解析已有输出，不默认插入逐步回调 |
| 页面 | 单窗口单 WebView，按需加载，日志限行，图片列表分页或虚拟化 |
| 窗口后台 | 最小化时降低事件消费与渲染频率，暂停非必要预览 |
| 更新频率 | 状态事件合并，普通界面约每秒更新 1～2 次 |
| GPU 监控 | 单一低频采集器，可关闭，不重复启动查询进程 |
| 数据集 | 引用原目录，缩略图惰性生成并缓存 |
| 模型 | 引用用户路径，不默认复制大型基础模型 |
| 结果预览 | 优先使用引擎已有采样，不加载独立推理管线 |
| 环境占用 | 候选安装按需执行，支持依赖下载缓存与引用感知清理 |

若日志消费出现背压，应优先降低解析与界面更新频率；不能让界面读取速度决定训练能否继续。磁盘耗尽等无法消除的问题必须明确报错，不能无声丢失任务状态。

### 8.2 GPU 资源策略

- 首版默认单 GPU、单活动训练任务，其余任务排队。
- 启动前检查显存与设备状态，并提示其他进程可能造成资源冲突。
- 不自动杀死 ComfyUI 或其他 GPU 程序。
- 显存估计仅作为建议，不承诺某配置一定不会 OOM。
- 多 GPU 与并发训练后续加入，默认仍优先稳定性。

### 8.3 性能验收方法

使用同一引擎版本、环境、模型、数据集及配置，对比直接 CLI 启动与本应用启动。

- 测量稳态训练吞吐，目标是包装层导致的下降不超过约 1%；这是待测试目标，不是未经验证的承诺。
- 排除首次加载、编译和缓存阶段，分别记录采样与 checkpoint 保存开销。
- 多次运行，报告波动范围；测量误差较大时不得据单次结果宣称达标。
- 确认管理进程不产生额外 CUDA 上下文。
- 开发完成后的常规性能验收记录空闲、训练监控和数据集浏览时的资源占用，覆盖桌面层、后端、监管与 WebView 子进程；不另设前端选型验证阶段。
- 长时间训练中，日志增长不能导致前后端内存持续无界上涨。

## 9. 技术栈与工程组织

### 9.1 技术方案（前端已确定）

- 桌面窗口：pywebview；Windows 固定使用 WebView2 渲染路径。
- 前端：TypeScript + Vue 3 + Vite，构建为静态资源，在桌面窗口内运行。
- 后端：Python + FastAPI + Uvicorn，运行于独立应用环境。
- 前端事件：优先 SSE，操作走 HTTP；若后续确有双向实时通信需求再引入 WebSocket。
- 监管与进程控制：Python，优先标准库，避免引入任务队列平台。
- 存储：SQLite + 文件系统。
- 配置：版本化 schema，输出各引擎原生 YAML、TOML 或 JSON。
- 环境安装：评估 `uv`，保留 `venv + pip` 兼容路径，以实际引擎安装验证为准。
- 分发：首版提供桌面启动入口和预构建前端；发行包逐步完善，但桌面窗口本身属于首版范围。

不引入 Redis、Celery、Electron 或强制 Docker。应用后端框架不参与训练执行，不应成为引擎依赖的一部分。

### 9.3 平台策略

优先验证 Windows + NVIDIA 单 GPU 的端到端流程，同时保持路径、进程控制与环境安装接口可替换，以便后续支持 Linux。

某引擎或架构若在 Windows 尚未验证，必须标注状态；不以“上游可以运行”替代本项目验证，也不默认要求用户使用 WSL。

### 9.4 前端实现方案

#### 9.4.1 窗口与服务启动

桌面入口负责启动或连接应用后端，等待本地服务就绪后创建主窗口并加载静态前端。窗口与后端生命周期解耦，任务监管独立存在。所有应用启动的后台进程默认不弹出无关控制台窗口。

桌面层不运行训练脚本，也不暴露可任意执行 Python 或 shell 的接口。原生桥接采用明确的允许列表，只提供文件/目录选择、窗口状态等必要能力；业务操作统一通过受校验的后端 API。

#### 9.4.2 页面与组件

采用单页应用和“左侧导航 + 右侧工作区”：概览、引擎管理、数据集、新建训练、训练任务、训练结果、设置。

- 使用 Vue 单文件组件与 TypeScript，按业务模块拆分。
- 使用 CSS 变量组织主题，隔离组件样式，不依赖外部 CDN、在线字体或其他在线页面资源。
- 统一封装输入框、选择器、表格、弹窗、状态标签等基础控件。
- 图表与原生配置编辑器按需加载，不在启动时加载全部重型组件。
- 首版不为每个引擎复制一套页面，组件库的具体取舍不改变已确定的前端技术方案。

引擎管理作为一级页面，直接展示 `engine/` 发现结果、安装实例、版本、环境就绪状态和默认选择。

#### 9.4.3 训练表单

采用“固定基础表单 + 能力驱动参数 + 原生配置预览”的混合方式：

- 模型、数据集、输出目录和任务名称使用固定设计的基础表单。
- 引擎适配器声明参数类型、默认值、范围、分组与版本限制，后端转为结构化描述提供给前端。
- 引擎专属字段独立分组，不假定同名参数跨引擎等价。
- 参数变化后由后端校验，展示最终原生配置与启动参数。
- 前端不读取或执行 `adapters/` 代码；版本能力变化优先在适配器档案中处理。

#### 9.4.4 API、事件与本地路径

- HTTP 用于查询、保存配置、启动、停止与引擎管理操作。
- SSE 已用于任务状态、训练进度、日志与受限增量通知；安装进度待托管安装功能实现。
- 重连后先获取状态快照，再恢复增量事件；日志只请求必要尾部或分页内容。
- 普通状态约每秒更新 1～2 次，日志采用批量更新和限行展示。
- 本地模型、数据集、引擎与解释器路径使用原生选择对话框或手动输入，不通过浏览器上传大文件。
- 原生对话框返回的路径仍由后端进行访问范围、文件类型、存在性和覆盖检查。
- 图片分页或虚拟化加载，只请求缩略图，不一次解码全部原始图片。

#### 9.4.5 性能边界与实施决策

前后端及窗口层不加载训练模型、不接入训练 step；桌面 WebView 的渲染资源开销不能混同为训练框架开销，也不能声称零内存或零 GPU 占用。

默认保留正常的硬件加速，不把全局禁用 GPU 当作低开销前提。通过单 WebView、限量缓存、批量事件、惰性加载和最小化降频控制开销。

**该方案已确定，直接进入实现，不做前端技术对比原型或独立性能验证。** 项目既有训练可靠性测试和开发完成后的常规验收不作为前端技术选型门槛。

## 10. 安全与数据保护

- 默认仅绑定本机地址；远程访问不属于首版默认能力。
- 本地 API 仍需校验访问来源与会话，防止外部网页触发敏感操作。
- 桌面窗口只加载受控本机页面；不允许任意远程页面获取原生桥接能力，外部链接不得在具备桥接权限的主窗口中打开。
- 使用参数列表启动进程，不拼接可注入的 shell 命令。
- 文件操作限制在用户明确授权的目录，检查路径穿越、符号链接及目标覆盖风险。
- 删除环境、数据集或产物前展示实际绝对路径及影响范围。
- 对密钥、模型站点 Token、代理凭据进行脱敏，不写入普通日志或导出配置。
- 密钥通过受控运行环境或系统凭据存储传递，不放入可公开的任务摘要。
- 安装训练引擎会执行第三方代码，安装来源与版本必须可见，必要时要求用户确认。
- 下载与发布产物先写临时位置；异常中断后能够识别未完成文件。
- 不自动删除用户导入的外部环境、基础模型或原始数据集。

## 11. 开发里程碑

以下按交付顺序划分，不在未经实现评估前承诺固定工期。

### M0：工程骨架与契约（已完成，基础桌面/API 已实现）

交付：

- pywebview 桌面窗口、Vue 前端、独立 Python 后端与统一桌面启动入口，直接按确定方案实施。
- 配置 schema、适配器契约、引擎版本与安装实例模型、任务状态机。
- 数据目录与 SQLite 初始化。
- 模拟训练进程，验证日志、失败、停止及任务持久化。

验收：不安装 ComfyUI、不安装真实训练引擎，也能完成模拟任务闭环。

### M1：第一个真实训练闭环（Kohya 功能已实现，真实 GPU 验收待完成）

范围：Kohya / sd-scripts、SDXL、单 GPU。

交付：

- 将引擎复制进 `engine/` 后发现和识别，选择已有运行环境，登记安装实例并固定任务使用的版本。
- 本地模型与数据集引用。
- 基础训练配置、原生配置预览与校验。
- 启动、监控、停止、产物登记。
- 手动发布选定 LoRA 到用户指定目录。

验收：一个真实任务完成训练；记录与原生 CLI 的性能对比；训练器未安装或启动 ComfyUI 仍可正常工作。产物在验证环境中的 ComfyUI 加载测试单独进行，不成为训练器运行依赖。

### M2：可靠任务运行与引擎管理（队列、绑定与重连已实现，其余待开发）

交付：

- 独立监管进程、任务队列与后端重连。
- 托管安装、诊断、多版本共存、默认版本选择、任务版本固定、候选更新、回滚与引用保护卸载。
- 恢复能力声明、有效保存点识别和恢复任务创建。
- Windows 进程树与长时间日志测试。

验收：同一引擎至少两个安装实例可共存和选择；关闭桌面窗口、重启应用后端不影响活动训练；失败更新不破坏旧环境；默认版本切换不改变排队任务的执行版本；卸载操作不会删除活动任务或其他安装实例依赖的资源。

### M3：第二引擎与适配扩展验证（识别/诊断已实现，训练待开发）

范围：AI Toolkit，先选择一个明确架构，例如 FLUX.1 LoRA，具体平台与环境需验证后确定。

交付：

- 原生 CLI 和配置适配。
- 能力矩阵、引擎专属参数与版本测试档案。
- 日志、指标、停止与产物解析。
- 界面明确展示不可跨引擎等价转换的字段。

验收：接入第二引擎不需要重写任务、存储和界面主体；经过验证的训练产物可在目标 ComfyUI 测试环境中使用。

### M4：体验与实验管理增强

交付：

- 批量 caption 编辑、预处理任务。
- checkpoint 对比、实验记录与参数扫描。
- 更丰富的模型架构和版本档案。
- 多 GPU 调度与更完善的分发安装。

远程执行和多人协作作为后续独立需求，不默认纳入 M4；pywebview 桌面窗口已纳入 M0，不再作为后续可选外壳。

## 12. 测试与持续维护

### 12.1 自动化测试

- 单元测试：配置映射、路径校验、能力声明、日志解析与状态转换。
- 快照测试：固定输入生成的原生配置与参数列表。
- 模拟进程测试：输出洪峰、异常退出、超时、停止、残留子进程、断线重连。
- 安装测试：失败重试、候选目录清理、旧版本保持可用。
- 复制接入测试：任意目录名、无 Git 副本、多版本匹配同一适配器、识别冲突、缺失依赖、失效的复制环境及用户目录保护。
- 版本管理测试：tag/分支解析、同代码不同环境、多版本选择、默认切换、任务绑定、外部环境变化、离线使用及卸载引用保护。
- 产物测试：未完成文件、同名冲突、缺失 checkpoint 与发布失败。
- GPU 集成测试：对选定的引擎和架构运行小规模真实训练，不在普通单元测试中下载大模型。

### 12.2 上游维护流程

```text
监测上游变更
→ 建立候选版本档案
→ 检查 CLI 与配置变更
→ 更新适配器及日志测试样本
→ 验证安装与最小训练
→ 更新兼容矩阵
→ 发布可用版本
```

“持续更新”应由测试、兼容档案和可回滚分发实现，而不是只提供一个 `git pull` 按钮。

## 13. 关键风险与应对

| 风险 | 应对 |
| --- | --- |
| 上游 CLI、配置或日志变更 | 固定 revision、版本化适配器、保留原始日志和解析样本 |
| 引擎依赖冲突 | 独立环境，不修改应用和其他软件环境 |
| Windows 支持不一致 | 按引擎与架构分别验证，明确标注未经验证组合 |
| 更新体积和安装失败 | 下载缓存、候选安装、可重试与回滚 |
| GPU 资源冲突 | 启动前检查与提示，不擅自终止外部程序 |
| 中断导致状态或产物损坏 | 区分停止语义，检查有效保存点，强制终止提示 |
| 数据集被外部修改 | 记录快照信息，提供可选冻结副本 |
| 输出无法在目标模型上使用 | 记录架构与基础模型，在明确组合上做加载验证 |
| 监控影响吞吐 | 低频采集、批量日志、旁路解析和 CLI 对照测试 |
| 功能范围失控 | 先完成单引擎真实闭环，再扩展引擎与高级功能 |

## 14. 总结与下一步

确定方案：**pywebview 桌面窗口 + Vue 3 前端 + 独立 Python 后端 + 成熟训练引擎适配器 + 隔离环境 + 轻量任务监管 + 版本化维护。**

ComfyUI 只作为训练产物的主要使用场景，不进入应用运行依赖、训练调度或环境安装链路。

下一步在可信引擎、独立环境与本地模型上完成 Kohya / SDXL 的真实 GPU 训练验收，整理明确的版本兼容档案；随后补齐 AI Toolkit 原生训练适配和托管环境维护。当前不宣布任意引擎版本兼容，也不把已有实例选择当作自动下载、更新或回滚安装实现。优先保证训练可靠和数据安全，继续保持既有前端设计。
