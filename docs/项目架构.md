# LP LoRA Trainer 项目架构

- 版本：0.1
- 日期：2026-10-06
- 状态：已建立目录与接口骨架，具体业务待实现
- 依据：`项目计划.md` 0.4；本文细化实现边界，不更改已确认方案。

## 1. 架构原则

1. 独立桌面应用，不依赖 ComfyUI。
2. pywebview + Vue 3 / TypeScript / Vite + 独立 Python 后端，直接实施，不做前端选型原型。
3. 引擎源码进入 `engine/`，接口适配进入 `adapters/`，一个适配目录对应一种引擎。
4. 代码版本、运行环境和安装实例分别记录，提交任务时固定具体实例。
5. 训练交给原生 CLI，管理模块不加载模型、不初始化 CUDA。
6. 桌面、API、监管与训练进程解耦，避免关闭窗口结束训练。
7. 本阶段只建立架构骨架，不把未实现功能包装成可用功能。

## 3. 进程结构

```text
桌面进程：pywebview + Vue 页面
         │ 本机 HTTP / SSE
         ▼
应用后端：FastAPI + Uvicorn
         │ 带鉴权的本机 IPC
         ▼
独立监管进程
         │ 原生配置 + LaunchSpec
         ▼
独立训练进程：指定安装实例的 Python + 引擎 CLI
```

- 桌面与后端可以启动或连接，监管进程不得被窗口关闭级联结束。
- 原生桥接只允许路径选择和必要窗口操作，不负责训练或引擎安装。
- 默认只加载本机受控页面，不允许远程网页获得原生桥接权限。
- Python 后端与监管不创建训练框架 CUDA 上下文；WebView 自身渲染开销仍然存在，不能承诺界面零显存。
- 上述生命周期是实现约束，不是当前骨架已提供的运行能力。

## 4. 依赖方向

```text
frontend → 本机 API（不直接访问 Python 模块）
desktop → 本机 API + 受限系统接口
app.api → app.services → app.storage / adapters 契约 / 监管客户端
adapters.<engine> → adapters.base → app.schemas
supervisor → app.schemas / 进程控制 / 活动任务存储 / 适配器公共接口
原生引擎 → 自己的环境（不依赖应用代码）
```

`app.schemas` 保持轻量，不依赖 API 框架、数据库、桌面库或训练框架。监管的进程执行器只消费启动参数，日志与产物处理可以使用适配器公共接口。

禁止：

- 应用直接 `import` 用户复制进来的引擎模块。
- 从 `engine/` 自动执行未知插件或注册脚本。
- 前端绕过后端执行 shell、改文件或启动训练。
- 适配器控制窗口、提供 HTTP 路由或改写任务队列。
- 在应用的 Python 环境中安装训练引擎依赖。

## 5. 引擎目录与版本模型

```text
engine/kohya_ss/      ─┐
                      ├→ adapters/kohya/
engine/kohya_ss-old/  ─┘
engine/ai-toolkit/     ─→ adapters/ai_toolkit/
```

目录名只是安装实例标签，不用来代替身份核实。适配器静态识别文件结构，检查引擎实际训练入口；不强制修改上游结构。

公共类型已放在 `app/schemas/engine.py`：

- `EngineRevision`：来源、请求的引用、commit、本地源码指纹。
- `EngineInstallation`：实例 ID、引擎类型、源码路径、管理方式、版本、环境与解释器。
- 安装状态与验证状态分开，默认选择单独持久化，不混成一个状态字段。

同一个代码版本可以对应多个运行环境。无 Git 信息的副本可登记源码指纹，不虚构上游版本。用户复制源码默认为用户管理；后续应用的更新和清理不能静默覆盖它。

## 6. 公共适配接口

`adapters/base.py` 定义 `EngineAdapter`，各引擎后续实现：

| 接口 | 职责 |
| --- | --- |
| `detect` | 静态检测类型及版本线索，不执行引擎 |
| `capabilities` | 返回支持架构、参数与版本限制 |
| `validate` | 验证配置，输出结构化问题 |
| `write_native_config` | 将原生配置写到任务目录 |
| `build_launch` | 返回参数数组、工作目录和运行环境覆盖项 |
| `parse_log` | 提取已知事件，未知日志保留原文 |
| `recovery_capabilities` | 分别声明正常停止、权重续训、完整状态恢复 |
| `collect_artifacts` | 登记产物及完整性，不把写入中的文件当成可用模型 |

`profiles/` 维护版本及环境规则，`templates/` 维护原生配置。安装、诊断和版本解析的具体流程在引擎服务实现阶段补齐，不在当前接口中伪造实现。

适配器需显式注册。类型冲突由用户确认，不根据目录名强制绑定。新增版本优先更新已有适配目录，不创建一个版本一份适配代码。

## 7. 任务与执行契约

`app/schemas/training.py` 已定义：

- `TaskState`：草稿、校验、排队、准备、运行、停止中、已停止、成功、失败、连接丢失。
- `TaskBinding`：安装实例、源码记录、环境清单、适配器与 schema 版本。
- `LaunchSpec`：参数数组、工作目录、仅运行时使用的环境覆盖项。
- `TrainingEvent`：事件类型与结构化内容，后续按事件种类细化字段。

任务进入队列之前必须完成配置校验和绑定；环境未就绪的安装实例不能进入队列。修改默认引擎不会修改已提交任务。

`LaunchSpec` 不使用 shell 命令字符串。密钥不得直接落入 `command.json`，只能记录脱敏的运行信息。状态存储和 IPC 需要保证活动任务只有一个状态写入方。

## 8. 核心数据流

### 8.1 复制接入

```text
复制到 engine/<任意实例名>/
→ 引擎服务枚举一级子目录
→ 静态调用受信任适配器 detect
→ 登记源码身份与安装实例
→ 用户选择解释器，检查环境
→ 状态就绪后允许训练
```

发现不等于执行；只有源码也不等于环境齐备。复制来的虚拟环境必须核实，不因存在 `.venv` 就判定可用。

### 8.2 提交训练

```text
前端编辑表单
→ 后端获取实例能力并校验
→ 固定 TaskBinding，生成任务目录与原生配置
→ 向监管提交任务
→ 监管复核实例后按队列启动 LaunchSpec
→ 原始日志落盘，解析事件增量返回
→ 后端 SSE → 前端限频展示
```

### 8.3 完成与交付

```text
训练结束
→ 监管登记退出状态与有效产物
→ 结果页展示配置、版本、模型和采样图
→ 用户显式选择 checkpoint
→ 后端发布到指定目录（可选 ComfyUI LoRA 目录）
```

训练不调用 ComfyUI。发布须检查覆盖风险，采用临时文件落盘，不复制全部 checkpoint。

## 9. 运行数据布局

默认路径由 `AppPaths` 定义，后续设置服务允许分别修改：

```text
engine/                         # 用户引擎，可迁移到其他磁盘
data/                           # 可配置 data_root，按需创建
├─ envs/<engine>/<environment_id>/
├─ manifests/
├─ datasets/                    # 索引/定义，不默认复制源图片
├─ jobs/<job_id>/
│  ├─ job.json
│  ├─ config.native.*
│  ├─ command.json
│  ├─ stdout.log
│  ├─ metrics.jsonl
│  ├─ artifacts.json
│  └─ runtime.json
├─ cache/
└─ state.sqlite
```

当前未创建运行数据或数据库，不在导入时初始化。`engine/` 内除说明文件外忽略版本控制，用户副本不属于应用更新范围。

模型和数据集使用外部路径引用。SQLite 保存索引与状态，不保存完整模型、图片和日志。应用导入的外部环境只登记，不接管其删除权。
