# LP LoRA Trainer 运行与安装

- 更新日期：2026-10-07
- 范围：独立桌面应用启动、引擎识别、官方环境安装、日志、解释器回写与诊断。
- 不改现有前端布局、主题与组件样式；不依赖 ComfyUI。

## 1. 用户操作

1. 保留完整交付目录：`LP-Lora-Trainer.exe`、`python_runtime/`、应用源码、`scripts/`、`frontend/dist/`、`assets/`。
2. 将可信训练器 clone/复制到 `engine/<实例名>/`，无需事先安装 Python 或创建 `.venv`。同类多个版本可放不同目录。
3. 双击 EXE，进入引擎页，刷新发现并确认类型。识别依据源码特征，而非必须使用固定文件夹名。
4. 点击“安装引擎环境”，确认信任源码；无需先绑定解释器。Musubi 可选择该版本声明的 CUDA extra，其他引擎由官方安装器决定依赖。
5. 应用跳到终端，依次执行安装步骤并显示原始输出，可停止安装。
6. 安装器退出成功后，应用自动发现引擎 Python、先保存路径，再诊断依赖/设备并回写状态。任何一步失败均不显示安装成功，查看终端及引擎问题详情后重试。
7. 只有已实现训练适配且诊断就绪的实例可提交训练。AI Toolkit 与 Musubi 当前可安装/管理环境，但不能提交真实训练。

**已有独立环境：** 可通过“选择 Python”绑定引擎目录内部现有解释器并执行诊断；不允许使用应用 `python_runtime`、系统 Python 或其他引擎目录的 Python。后端同时检查可执行文件路径和解释器实际 prefix，不只看文件名。

## 2. 进程链路

```text
LP-Lora-Trainer.exe（相对自身目录定位，无 CMD）
  → python_runtime/pythonw.exe → desktop.launcher.run()
  → 本机 API（首次启动，或认证后重连已运行的同数据目录 API）
  → frontend/dist（不需要 Node 开发服务）
  → 引擎扫描 → adapters/<engine>/
  → 安装会话登记 → 准备项目内 uv / 基础 Python
  → 引擎安装子进程（无控制台、实时输出）
  → 保存发现的引擎 Python → 真实子进程诊断 → 持久化状态
```

桌面、API、supervisor 和训练子进程解耦。关闭窗口不会结束后台 API 或训练；重新打开窗口可连接原后端，但必须通过安装协议版本检查；旧版缺少协议或协议不匹配时启动器明确拒绝，并写日志/弹窗，不会静默重用旧流程或另起同端口后端。更新代码后，仅关闭窗口再打开**不会替换已运行的旧 API**：需先停止安装/训练并退出旧后台，再启动新版 EXE。不要在活动任务期间强制结束后台。在任务管理器“详细信息”中显示命令行列，核实本项目 `python_runtime\pythonw.exe` 的 `-m app.api.server` 与 `-m supervisor.worker` 进程；仅在任务已停止后退出这些已核实的进程，不要批量结束所有 Python。

桌面未处理异常写入 `runtime/desktop.log`，弹窗说明日志位置；API 启动输出在 `runtime/backend.log`。命令行入口和 EXE 都使用同一桌面错误处理函数。

## 3. 环境分层

| 目录 | 职责 |
| --- | --- |
| `python_runtime/` | 完整便携 CPython 和轻量应用依赖，启动桌面/API/supervisor，仅运行标准库安装引导；不装 torch 等训练依赖 |
| `runtime/uv/uv.exe` | 项目内环境管理工具；已有文件直接使用，缺失时从官方 release 获取 |
| `runtime/uv/python/` | uv 管理的基础 Python；不要求安装系统 Python |
| `runtime/uv/cache/` | uv 下载/安装缓存 |
| `engine/kohya_ss/venv/` | Kohya 独立 Python 与训练依赖 |
| `engine/ai-toolkit/.venv/`（或官方已有 `venv/`） | AI Toolkit manager 管理的独立环境 |
| `engine/musubi-tuner/.venv/` | Musubi uv 项目环境 |
| `data/installations/<session-id>/output.log` | 安装会话完整日志，随 `--data-root` 改变 |

引擎的 `.venv` / `venv` **不是依赖应用运行环境的开发 `.venv`**。基础 Python 在项目内由 uv 管理，虚拟环境仍依赖其基础 Python 和 OS/GPU 驱动；“独立”不等于任意路径迁移后无需重建。

安装子进程清理继承的 PYTHON/PIP/UV/Conda 配置，设置项目 uv、缓存和 managed Python 目录。AI Toolkit 若已有仓库内 uv，会按其官方 manager 的优先级使用；LP 不修改其源码。

## 4. 各引擎安装入口

安装计划依据当前仓库内官方脚本，不把任意训练器替换成通用 `pip install -r requirements.txt`。

### Kohya

1. 项目 uv 创建引擎内 `venv`，使用 managed Python 3.11 并 seed pip。
2. 引擎 Python 执行官方 `setup.bat` 中的 setuptools 前置步骤：`-m pip install --require-virtualenv --no-input -q setuptools`。
3. 使用引擎 Python 执行 `setup/setup_windows.py --headless`；显式将 `setup/` 放入导入路径，兼容隔离 Python 的脚本导入。
4. 官方安装器负责 sd-scripts 子模块初始化和 CUDA 依赖。普通 clone 缺子模块时允许开始安装；安装后再检查完整训练源码。

只放底层 sd-scripts 的实例可识别和绑定已有环境，但若不含 Kohya 官方 `setup/setup_windows.py`，此 Windows 安装按钮明确拒绝，不猜测安装命令。安装接口当前仅支持 Windows。

### AI Toolkit

使用应用运行时启动源码中的 `manager/__main__.py install`。该标准库入口自行管理基础 Python、虚拟环境、PyTorch、requirements，并按官方流程处理 Node/ffmpeg；应用运行时不接收训练依赖。缺 manager 的旧版本明确拒绝，不回退到猜测的 pip 流程。

### Musubi Tuner

调用项目 uv：`uv sync`，或 `uv sync --extra cuXYZ`。可选 extra 从该实例 `pyproject.toml` 获取，未声明的 CUDA 选项会拒绝。`existing` 表示不传 extra、仍按项目默认依赖同步，**不是跳过安装或保证保留所有已装包**。基础 Python 版本由该项目元数据决定。

### 镜像源设置

“安装引擎环境”弹窗的 **Python / uv 镜像源** 可选择官方 PyPI、清华大学镜像、阿里云镜像或自定义 HTTP(S) URL。默认使用官方源，每次安装可单独选择，不修改系统 pip 配置或引擎源码。

- 选择镜像后，后端将地址传给当前安装进程及子进程的 `PIP_INDEX_URL`、`UV_INDEX_URL` 和 `UV_DEFAULT_INDEX`；终端记录本次选择，安装会话保存 `mirror_url`。
- 自定义地址必须包含 `http://` 或 `https://` 和主机名，不允许用户名密码、内部空白/控制字符或无效端口；错误地址在安装开始前拒绝，不创建安装会话。
- 镜像仅影响普通 Python 包索引，**不替代引擎官方安装器**。上游显式指定的 PyTorch/CUDA 源仍由上游管理；尤其 Musubi 的 CUDA extra 和专用源仍使用该实例 `pyproject.toml` 与 `uv sync` 流程。
- Git/GitHub、uv 可执行文件、基础 Python、Node/ffmpeg 等不通过 PyPI 下载的资源不会被该选项加速。镜像缺包或网络失败不会自动静默切回官方源，请检查日志后重新选择源安装。
- 安装进程清理宿主机继承的 pip/uv 索引及 Python/虚拟环境变量，并禁用宿主机 pip 配置，避免与选择冲突；不改写这些宿主机配置文件。引擎自己的项目配置及命令行选项仍保留。

升级后如桌面提示旧后台安装协议不兼容，先停止安装/训练并确认进程已退出，再退出本项目旧 API 和 supervisor 后重新打开 EXE。仅关闭桌面窗口不会退出后台；不要在活动任务期间强制结束后台进程。

### AI Toolkit 历史乱码恢复

旧记录中 AI Toolkit 提示文字的 `�` 或连续问号会在读取/刷新发现时被适配器的正常 Unicode 提示替换，不删除数据库，也不丢弃真实安装失败信息。源码中的 Unicode 长破折号是有效 UTF-8，不因为 Windows 控制台显示问题而修改用户 clone 的上游源码。

## 5. 安装状态与失败恢复

```text
queued → running（逐条命令执行）→ verifying（保存环境并诊断）→ succeeded
              ├→ stopping → cancelled
              └→ failed
API 重启发现未完成会话 → interrupted
```

- 安装器非零退出、缺源码/解释器、诊断失败、元数据保存失败均不能报告成功。
- 一次仅允许一个安装；活动训练阻止环境安装，防止依赖被并发改动。
- 安装期间拒绝冲突的引擎操作；诊断阶段不接受取消，避免回写到一半。
- Windows 停止使用进程树终止，关闭 stdin，日志继续保留，不打开额外 CMD。
- 失败/取消后尽力发现并保存已经创建的解释器，环境路径不因诊断失败而丢失；修复后可重新安装/诊断，不自动删除用户环境或源码。
- API 重启将 queued/running/stopping/verifying 会话标为 interrupted，不冒充成功，也不自动重跑官方安装。重启中断不证明旧安装进程已退出，重试前请确认旧进程已停止。
- 终端支持会话切换、日志复制、显示清空和实时轮询；清空显示不删除 `output.log`。
- 日志 offset 按字节递增，分块边界保留未完整 UTF-8 字符，避免中文乱码；前端剥离 ANSI 控制码但持久化保留原始输出。

### 网络失败

首次安装要联网下载 uv、基础 Python 和训练包；GitHub / 包源不可达属于真实失败，不跳过步骤也不显示就绪。网络修复后可重试同实例，已有 uv 不覆盖，安装器是否修复部分环境由上游决定。

可从 Astral 官方 uv release 获取对应架构的压缩包，手动解压 `uv.exe` 到 `runtime/uv/uv.exe`，然后重试。不使用不明镜像，不依赖系统 pip。代理环境变量如 HTTP_PROXY/HTTPS_PROXY 可以传递给下载器，其他上游工具的网络配置以其文档为准。

## 6. 迁移与平台边界

- 完整应用目录可迁移，不绑定 D/H 盘，也不依赖系统 Python；EXE 仅以自身位置定位随包解释器。
- Windows 仍需 WebView2 Runtime、可用的 .NET Framework；引擎首次安装还需网络和其官方脚本要求的 Git 等工具，训练需要兼容的 GPU 驱动。
- 消费端无需预装 Python、pip 或 Node；AI Toolkit 安装器可能按官方流程自行安装 Node。
- 已安装引擎虚拟环境与数据库内绝对路径不保证随整目录迁移自动恢复；先停止相关进程，再迁移，随后重装环境或重新绑定路径并诊断。不要批量修改历史任务绑定。
- 当前不自动下载主仓库、不提供版本自动更新/回滚/卸载，不制作可任意路径迁移的整套训练环境包。

已验证：

- 镜像 URL 归一化/异常拦截、三种引擎环境策略的 pip/uv 参数传递、宿主包源隔离、会话记录和终端输出；真实本机 HTTP 请求到测试安装子进程的镜像参数贯通，不访问镜像或安装训练依赖。
- AI Toolkit 历史提示乱码在读取/刷新后修复并持久化，真实安装错误与单个问号诊断保留，其他引擎提示不受影响；本机会话失效/前端未构建的中文 API 提示正常。
- 便携运行时依赖/原生扩展/.NET 桥接/隔离环境/子进程自检。
- 真实本机 HTTP、真实安装子进程、日志读取、退出失败重试、Windows 进程树取消、真实引擎 Python 路径探测和回写；依赖/GPU 诊断使用测试 fixture。
- 官方安装命令选择、Musubi 动态 extra、Kohya 脚本导入与 setuptools 前置流程。
- uv 下载/解压/原子替换失败清理、环境创建失败、安装生命周期、桌面启动错误处理，以及旧后台安装协议不兼容时拒绝复用/拒绝重复启动的测试。
