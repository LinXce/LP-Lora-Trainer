## 1. 现象

双击 `LP-Lora-Trainer.exe` 后**桌面窗口不出现**。`runtime/desktop.log` 记录到（由 `desktop/launcher.py::_startup_error` 写入）：

```
desktop/launcher.py → open_window() → webview.start(gui="edgechromium")
  → pywebview WinForms → import clr → pythonnet.load()
  → clr_loader/netfx.py:47
RuntimeError: Failed to resolve Python.Runtime.Loader.Initialize
  from H:\SDaki\LP-Lora-Trainer\python_runtime\Lib\site-packages\pythonnet\runtime\Python.Runtime.dll
```

历史行为（修复前）：launcher 是"先起后端、再建窗口"，窗口失败后**后端与监管进程成为孤儿**，用户看到"两个 python 进程卡住、打不开"。
现已改为**先预检、失败则回退**，因此不再产生孤儿进程（见 §5）。

## 3. 已确认为事实的结论（均有命令/输出证据）

1. **故障真实、非工具沙箱造成**：用户自己在 17:43 与 17:51 双击产生的 `desktop.log` 记录就是同一错误（沙箱之外的进程）。
2. **可稳定复现**（在本会话沙箱内）：
   ```powershell
   cd H:\SDaki\LP-Lora-Trainer
   .\python_runtime\python.exe -c "import clr"                        # → 同一 RuntimeError
   .\python_runtime\python.exe scripts\check_runtime.py               # → 同一错误
   .\python_runtime\python.exe -m unittest tests.test_portable_runtime # → 该用例失败于同一错误
   ```
3. **coreclr 是被封死的另一条路，不要走**：
   - `PYTHONNET_RUNTIME=coreclr` 时 `import clr` **成功**（加载 .NET 6.0.36）；
   - 但 `webview.platforms.winforms` 需要 `System.Windows.Forms`（需在 runtimeconfig 里声明 `Microsoft.WindowsDesktop.App`）、还需要 `Microsoft.Win32.SystemEvents`；
   - 都补上后仍失败于：`TypeLoadException: Could not load type 'System.Windows.Forms.ContextMenu' from 'System.Windows.Forms, Version=6.0.2.0'`，来自 pywebview 导入 `Microsoft.Web.WebView2.WinForms`。
   → **随包的 WebView2 .NET 程序集是 .NET Framework 版本，只能在 .NET Framework（netfx）下工作**。
4. **程序集与 .NET Framework 本身看起来正常**：
   - `Python.Runtime.dll` 是合法的 `netstandard2.0` MSIL 程序集（`Python.Runtime, Version=3.2.0.0, PublicKeyToken=5000fea6cba702dd`，451072 字节）；
   - 全盘只有这一份副本；**无 Zone.Identifier（未被 MOTW 阻止）**；
   - 在 .NET Framework 宿主（Windows PowerShell 5.1）里 `[System.Reflection.Assembly]::LoadFrom("<该 dll>")` **当前可以成功**，且能找到类型 `Python.Runtime.Loader`。
   - ⚠️ 但同一调用**早先失败过一次**：`HRESULT 0x80131515 (COR_E_NOTSUPPORTED)`，几分钟后再试又成功 → 存在**间歇性**因素（详见 §4）。
5. **与路径/盘符无关**：从 C: 与 H: 调用 `LoadFrom` 都成功；同样的失败在 `%TEMP%` 副本里也出现过（注意本会话 TEMP 被重定向，见 §6）。
6. **原生 shim 架构正确**：`clr_loader/ffi/dlls/amd64/ClrLoader.dll` = AMD64、`dlls/x86/ClrLoader.dll` = I386，哈希不同；运行时 Python 是 **64 位**（3.12.7 AMD64, MSC v.1941）。
7. **控制台创建本身没问题**：从 pythonw（无控制台父进程）派生 `CREATE_NEW_CONSOLE` 子进程时，子进程能拿到真实控制台与可用 stdio（`GetConsoleWindow()!=0`、`print` 正常）。
8. **与 pythonnet 版本**：在沙箱内 `pythonnet 3.0.5 + clr-loader 0.3.1` **同样失败**（所以"仅换 pythonnet 版本"未被证明有效；但见 §6 的沙箱限制，此结论需在干净环境重测）。
9. **EXE 宿主无辜**：`desktop/launcher_host.cs` 只是 `Process.Start("python_runtime\pythonw.exe", "-m desktop.launcher")`（`UseShellExecute=false, CreateNoWindow=true, WindowStyle=Hidden`）后立即返回。
10. **与安全策略的明显项**：Smart App Control **关闭**（`VerifiedAndReputablePolicyState=0`）、无 AppLocker 策略、CodeIntegrity 日志只有 Chrome 的签名告警、Defender 无威胁检测记录。
    但：**VBS/HVCI 处于运行状态**（`VirtualizationBasedSecurityStatus=2`，`SecurityServicesRunning={2}`），且 10/08 白天 Defender 配置被多次更改。

## 4. 剩余假设（按可能性排序）

1. **CLR 激活 / AppDomain 创建失败**（我最看好的方向）。
   失败点在 `clr_loader/netfx.py::_get_callable`：`_FW.pyclr_get_function(...)` 返回 NULL。而 `netfx.py:25` 调用的
   `self._domain = _FW.pyclr_create_appdomain(domain_s, config_file_s)` **没有检查返回值是否为 NULL** —— 如果 AppDomain 创建失败，后续取函数必然 NULL，报错文本就会是现在这样。
   → 需要插桩/跟踪，确认是"程序集加载失败"还是"AppDomain 根本没建起来"。
2. **安全软件间歇性拦截程序集加载**：`0x80131515` 的出现与消失 + Defender 配置变更 + HVCI 开启，符合这一模式。
3. **10/08 重启后的环境差异**：工作时间线显示 02:39 计划外关机后开始坏，而 .NET/pythonnet 文件都没变。
4. **pythonnet 3.2.0 / clr-loader 0.3.1 的 netfx 回归**：可能性较低（运行时未变），但不能排除"机器某状态 + 该版本"的组合问题。

## 5. 当前已实现的绕过（修复窗口时**不要**破坏它）

`desktop/launcher.py::main()` 的流程：

```text
检查 frontend/dist → 预检桌面桥接 desktop.window.desktop_bridge_error()
  ├─ 可用：ProcessLock(runtime/desktop.lock) → 起/复用后端 → open_window()   ← 不显示终端
  └─ 不可用：spawn_console() → cmd.exe /c runtime/browser-mode.cmd
             （系统终端，先 type assets/logo.txt 显示 LP 字标）
             → python -m desktop.console（读取 --reason-file）
             → 起/复用后端 → 默认浏览器打开 http://127.0.0.1:5900
             → 关闭该终端窗口 = 优雅结束后端 + 监管进程
```

- 行为契约（有测试锁定）：桥接可用时**不得**出现终端窗口；不可用时带**原因**回退且不静默失败；终端进程的 stdin 是 NUL 时**不得**被当成"用户按了回车"而退出。
- 相关测试：`tests/test_desktop_launcher.py`（15 项，全绿）。
- 默认端口：`app.config.DEFAULT_API_PORT = 5900`。
- 日志：`runtime/desktop.log`（launcher 异常）、`runtime/backend.log`（后端）、`runtime/console.log`（终端模式全过程）。

## 6. 环境陷阱（会误导判断，务必先读）

1. **本会话的工具沙箱会扭曲结论**：
   - 子进程（Python）**不能**在工作区之外创建目录（`WinError 5`）；
   - `TEMP/TMP` 被重定向进工作区（`tempfile.mkdtemp` 会落在 `H:\SDaki\LP-Lora-Trainer\` 下，这也是 `tests/test_portable_runtime.py` 的副本路径看起来在 H: 的原因）；
   - `Assembly.LoadFrom`、CLR 相关结果可能与普通用户 shell 不一致。
   → **任何结论都必须在"非沙箱"的交互式 cmd / 资源管理器双击下复验**；`runtime/desktop.log` 是唯一可信的真值来源。
2. `Start-Process -ArgumentList '-c', $多行代码` 会把多行参数拼坏（我曾因此得到一次**假**复现）。请写脚本文件再运行。
3. `taskkill` / WMI 过滤不要用 `-match '某个脚本名'`：它会匹配到你自己 shell 的命令行（我因此杀掉过自己的 shell）。请同时限定进程名。
4. 不要在不检查任务状态的情况下结束用户的后端/监管进程；先只读 `data/state.sqlite` 的 `kind='task'` 记录确认没有活动任务。
5. 后端和 supervisor 是**故意独立**的：关窗口不结束它们；整体退出要用 `POST /api/v1/system/shutdown`（无活动/失联任务时才允许）。

## 10. 明确不要做的事

- **不要**为了绕过而把 pythonnet 切到 coreclr 并宣称窗口可用：`Microsoft.Web.WebView2.WinForms` 依赖 .NET Framework 才有的 `System.Windows.Forms.ContextMenu`，coreclr 下必然失败（§3.3 已证）。
- **不要**为了"让它能开"而移除启动预检或把回退改成静默：当前回退会写明原因并落 `runtime/console.log`，这是刻意设计。
- **不要**在活动训练期间强杀后端/监管进程（会破坏"关闭终端/后端不终止训练"的既有契约）。
- **不要**把本机的 `pythonnet` 故障结论外推为"项目对所有机器都坏"：现象与这台机器的运行环境相关，便携运行时文件本身未被证明损坏（§3.4）。
