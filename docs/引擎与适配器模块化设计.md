# 引擎与适配器模块化设计

## 1. 设计目标

LP-Lora-Trainer 是面向 ComfyUI LoRA 工作流的独立训练器，不依赖 ComfyUI 运行，也不把任何训练器源码改造成主程序的一部分。项目将“训练引擎源码”和“LP 接口适配”分离，以便：

- 直接将引擎 clone 或复制到 `engine/` 后使用；
- 为每个训练引擎独立维护安装方式、参数能力、配置格式和日志解析；
- 在引擎升级时只替换对应源码或安装版本，不影响主程序和其他引擎；
- 新增引擎时不修改训练队列、任务历史、桌面窗口等主流程。

## 2. 目录职责

```text
engine/
├─ kohya_ss/             # Kohya / sd-scripts 源码，可由用户 clone 或复制
├─ musubi-tuner/         # Musubi Tuner 源码
└─ ai-toolkit/           # AI Toolkit 源码

adapters/
├─ base.py               # EngineAdapter 统一接口与数据契约
├─ registry.py           # 适配器自动发现、冲突隔离和能力目录
├─ sampling.py           # 跨引擎的采样提示词文本转换
├─ kohya/
│  ├─ adapter.py         # Kohya 适配器
│  └─ params.py           # 参数与能力声明
├─ musubi_tuner/
│  ├─ adapter.py
│  └─ params.py
└─ ai_toolkit/
   ├─ adapter.py
   └─ params.py
```

### `engine/`：引擎源码层

`engine/<engine-name>` 只保存上游训练器源码及其自身的文件。LP 不要求引擎源码实现统一 API，也不在这里放主程序业务代码。安装环境可以由引擎自己的安装脚本、`pyproject.toml`、`uv` 流程或其他适配器声明的安装命令创建。

引擎目录名称只是安装路径，**不能单独作为引擎类型判断依据**。类型由适配器对源码特征进行静态检测，必要时由用户在界面中确认。

### `adapters/`：接口适配层

每个引擎对应一个 `adapters/<adapter-id>/adapter.py`，其中定义且仅定义一个具体的 `EngineAdapter` 子类。适配器负责把 LP 的统一任务模型翻译为该引擎的原生模型，主程序不直接调用 Kohya、Musubi 或 AI Toolkit 的内部模块。

适配器可以声明：

- `engine_id`、显示名称、适配器版本；
- 源码静态检测规则和版本信息；
- 安装策略、环境目录、Python 候选和 CUDA 依赖；
- 支持的模型架构、参数能力和参数校验；
- 原生配置生成、启动命令和预览命令；
- 日志解析、停止/恢复能力和训练产物收集；
- 原生参数导出及配套文件。

## 3. 自动发现与运行链路

启动后 `adapters.registry.discover_adapters()` 扫描符合命名规则的适配器目录，并加载其中的 `adapter.py`。加载失败的适配器会被隔离并进入错误目录，不会阻止其他引擎继续工作；重复的 `engine_id` 会禁用冲突适配器，避免静默覆盖。

引擎使用链路如下：

1. `app.services.engines` 扫描 `engine/` 下的源码目录；
2. 调用所有已注册适配器的静态 `detect()`，不导入或执行引擎源码；
3. 生成候选引擎类型，必要时由用户确认类型；
4. 安装服务读取选中适配器的 `installation_plan()`，由适配器调用该引擎自己的安装流程；
5. 训练服务通过 `EngineAdapter.validate()`、`write_native_config()` 和 `build_launch()` 生成任务；
6. supervisor 仅使用适配器提供的命令启动训练，并使用适配器解析日志、停止任务和收集产物。

因此，主程序只面向 `EngineAdapter` 和统一的数据契约，不面向某个训练器的具体脚本。

## 4. 新增引擎规则

新增引擎不需要修改主程序训练逻辑，按以下步骤进行：

1. 将引擎源码 clone 或复制到 `engine/<目录名>`；
2. 在 `adapters/` 下新建符合小写命名规则的目录；
3. 添加 `adapter.py`，实现一个具体的 `EngineAdapter` 子类；
4. 添加该引擎的 `params.py`、流水线或其他适配器私有模块；
5. 在适配器中实现源码检测、安装计划、能力声明、配置生成、启动和日志解析；
6. 重启 LP，使注册表加载新适配器；
7. 在引擎页面刷新/重新扫描，确认 `engine/<目录名>` 被识别并绑定到新适配器。

“只复制引擎源码即可使用”适用于已有适配器的引擎；对于全新引擎，仍必须提供对应适配器，因为不同训练器的参数、命令、配置和日志格式并不相同。

## 5. 提示词模板与模块边界

提示词模板属于应用层数据，由 `app/services/prompt_templates.py` 负责持久化、校验和 CRUD，不导入任何具体训练器。主程序内部统一保存提示词文本，每行代表一个采样提示词。

`adapters/sampling.py` 是适配器层的公共转换工具：

- Kohya / Musubi 在任务目录生成 `sample_prompts.txt`，原生配置引用任务目录中的文件；
- AI Toolkit 将文本直接转换为原生 YAML 的 `sample.prompts` 列表；
- 旧配置中的提示词路径不会被误当成提示词文本。

这样，模板管理功能不会与某个引擎绑定，而是由具体适配器在导出和提交阶段完成引擎差异转换。

## 6. 当前实现核对结论

截至当前代码，模块化要求已满足：

- 主程序服务通过 `ADAPTERS` 和 `EngineAdapter` 工作，没有把某个引擎的训练实现写进通用训练流程；
- 当前 `kohya`、`musubi_tuner`、`ai_toolkit` 均采用独立适配器；
- 引擎安装由适配器的安装策略和安装计划负责；
- 引擎源码检测不依赖目录名，也不会在检测时执行引擎代码；
- 前端通过 `/api/v1/adapters` 和能力描述获取引擎信息，不维护训练器名称白名单；
- 提示词模板和采样提示词转换位于应用层/适配器公共层，未反向依赖某一个具体引擎；
- 适配器发现、重复 ID 隔离和插件错误隔离已有回归测试。

需要明确的边界是：适配器注册表在进程启动时加载，因此新增或修改适配器后需要重启 LP；引擎源码版本的重新识别则可以通过引擎页面的重新扫描完成。该行为是为了避免训练过程中动态替换适配器造成配置和运行时不一致。
